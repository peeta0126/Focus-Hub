# 성능 개선 측정 기록

## 결론

로그인 화면이 사용자가 제출하기 전에도 Supabase SDK와 범용 폼 검증 라이브러리를 내려받는 문제를 확인했다. 제출 시점 동적 import와 로그인 전용 경량 검증으로 초기 JS 전송량 중앙값을 323,800B에서 151,713B로 53.15% 줄였다. 같은 조건의 Lighthouse 5회 중앙값에서 LCP는 3,051ms에서 2,441ms로 20.00%, TBT는 62.5ms에서 23.5ms로 62.40% 개선됐다.

개별 실행값은 [`measurements.json`](./measurements.json)에 기록했다. 수치는 반올림 전 원본값으로 중앙값을 계산했으며, 측정하지 못한 값은 결과에 포함하지 않았다.

## 측정 범위와 조건

- 기준 커밋: `a94235aa8657cd7f560cfa845704f2c6efe400bd`
- 대상: 프로덕션 빌드의 `http://127.0.0.1:3100/login`
- 빌드/서버: Next.js 16.3.8의 `next build`와 `next start`
- 도구: Lighthouse CLI 13.5.0, Chrome 155, Node.js 24.14.0
- Lighthouse 기본 모바일 에뮬레이션: 412×823, DPR 1.75
- 시뮬레이션: RTT 150ms, 1,638.4Kbps, CPU 4배 slowdown
- 각 버전 5회 실행 후 중앙값 비교, 실행마다 Lighthouse가 스토리지를 초기화
- 측정일: 2026-10-22, 동일 PC와 동일 로컬 프로덕션 서버 사용

재현 명령은 다음과 같다. 각 측정 전 소스 버전에 맞춰 다시 빌드하고 서버를 재시작한다.

```powershell
npm run build
npm run start -- -H 127.0.0.1 -p 3100
npx --yes lighthouse http://127.0.0.1:3100/login `
  --only-categories=performance `
  --output=json `
  --output-path=docs/performance/run-1.json `
  --chrome-path="C:\Program Files\Google\Chrome\Application\chrome.exe" `
  --quiet
```

동일 명령을 출력 파일 번호만 바꿔 5회 실행한다. `resource-summary`의 script 전송량/요청 수와 `network-requests`의 전체 요청 수를 사용했다.

## 적용 내용과 실험 판단

1. `QuickAddModal`을 `next/dynamic`으로 분리했다. `/login`의 JS는 323,800B에서 322,385B로 0.44%만 감소해 단독 효과가 작음을 확인했다.
2. 로그인 제출 함수 안에서 Supabase 클라이언트를 동적으로 import했다. JS 중앙값이 254,552B로 감소했고 실제 제출 시 인증 API가 호출되는 것을 확인했다.
3. 로그인에 필요한 두 규칙만 로컬 검증으로 대체해 초기 `react-hook-form`/Zod 청크를 제거했다. 최종 JS 중앙값은 151,713B가 됐다.

기능/UI 보존 검증:

- `next build` 성공, TypeScript 검사 성공
- 변경 TSX ESLint 성공 및 `src` 전체 ESLint 성공
- 빈 폼 제출 시 기존 문구인 `올바른 이메일을 입력해주세요.`, `비밀번호는 6자 이상이어야 합니다.` 표시 확인
- 유효한 형식의 테스트 입력 제출 시 지연 청크 로드 후 Supabase 인증 요청이 발생하고, HTTP 400 응답을 기존 `이메일 또는 비밀번호를 확인해주세요.` UI로 표시함을 확인
- 전후 스크린샷의 로그인 레이아웃과 스타일이 동일함을 육안 확인

실제 계정으로 성공 로그인과 인증 후 빠른 추가 저장까지는 계정 정보가 없어 검증하지 않았다. 빌드/타입 검사로 해당 경로의 컴파일 안정성은 확인했지만, 이 제한을 성공한 E2E 검증으로 표현하면 안 된다.

## 자기소개서용 요약

문제 상황: 개인 생산성 대시보드의 로그인 진입점에서 사용자가 아직 제출하지 않았는데도 인증 SDK와 범용 폼 라이브러리가 초기 번들에 포함돼 있었다.

내 역할: 코드베이스와 Next.js 16 로컬 문서를 분석하고, 프로덕션 빌드에서 Lighthouse 기준값을 먼저 5회 측정했다. unused-JS 결과로 원인을 좁힌 뒤 기능 경계를 재설계하고 동일 조건 5회 중앙값으로 검증했다.

AI 활용 범위: AI는 병목 후보 탐색, Next.js 문서 확인, 측정 명령 실행, 코드 분리안 제안, 반복 측정값 정리에 활용했다. 최적화 채택 여부는 실제 Lighthouse 결과와 기능 테스트를 기준으로 판단했으며, 측정되지 않은 INP나 인증 후 API 성능은 수치화하지 않았다.

해결 과정: 사용 전 모달을 동적 분리하고, Supabase SDK를 로그인 제출 시점으로 미뤘다. 두 필드뿐인 로그인에서 범용 폼 검증 라이브러리를 제거하고 기존 오류 문구와 제출 상태를 유지하는 경량 검증으로 교체했다.

검증 결과: 초기 JS 323,800B→151,713B(-53.15%), LCP 3,050.96ms→2,440.66ms(-20.00%), TBT 62.5ms→23.5ms(-62.40%), Lighthouse 성능 점수 94→98을 달성했다. 빌드·타입·ESLint와 실패 인증 흐름을 확인했고, 성공 인증 경로는 테스트 계정 부재로 검증 범위에서 명시적으로 제외했다.
